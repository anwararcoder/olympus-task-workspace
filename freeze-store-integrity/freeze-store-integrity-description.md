# Freeze store integrity maintenance

**Category**: Feature Request

Ensure the `TextFileBasedViolationStore` maintains the integrity of its `stored.rules` index and files.

When naming files with `default.fileNames` it will default to `random`. Using `description` will produce a deterministic name based on the description of the rule. All instances of `\r\n` are considered `\n`. Each rule will produce a different name. If there is a full word made up of ascii characters and/or numbers that is between 4 and 120 characters long, one such word will be used, it can appear anywhere in a long description. File names built-in will consist of only ascii characters, numbers, underscore and dashes. They will not be longer than 200 characters and will never equal `stored.rules`.
Otherwise this value should be a class name that implements `RuleViolationFileNameStrategy` and have a public constructor that takes no arguments. The strategy passed into the constructor will also name files. If you specify a `default.fileNames` for a store that uses a `RuleViolationFileNameStrategy` it will not be accepted. This includes if the strategy was supplied by a `Properties` object passed into the constructor. Both strategies will receive the description of the rule as it was written including any `\r\n` when storing a rule. If no file name is generated from a strategy it will fail once a name is required.

The value of `default.integrity` must be one of `repair`, `fail` and `ignore`. Defaulting to `ignore` which checks nothing. `repair` and `fail` will check the index and folder during initialization. Any other value will fail stating the acceptable values.
If an entry points to a path that is not a file within the folder directly. It is considered broken. This also applies if the file name is not a valid path. If a file name points to a file that has no violations it is considered resolved. Files that only contain line breaks are also resolved (`\n`, `\r\n` or just `\r`). As previously mentioned the violation file has not changed its format. A violation with a `\r` in it will remain. If an entry has a file name that does not match the name it would generate for its rule it is considered misplaced. A misplaced entry is occupied if the name it generates is already being used. Either it exists, is being used by another entry or points outside of the folder. An entry that points to the name it would generate will never be occupied.

Multiple entries that point to the same file name are considered shared. This is true even if nothing exists with that name. If multiple entries point to the same file they are also considered shared. Including through a symbolic or hard link. Even if that file is outside the folder. Multiple entries that generate the same name are considered colliding. Any file in the folder that is not pointed to by an entry is considered unowned. Not including the index. The `TextFileBasedViolationStore` will not touch any shared entries or unowned files. It will never move an entry that is considered colliding or occupied. But will still discard an entry that is broken or resolved. If an entry is shared and anything else it will remain shared. Two rules that only differ in line breaks will be separate entries in the index. However when storing or loading a rule the line breaks will be considered equal.
When set to `repair` broken entries will be discarded. Resolved entries and the file they point to will be discarded. If a symbolic link is resolved the file it points to will be deleted as well. A misplaced entry will have its file moved to the correct file name. If it is a symbolic link the file it points to will be moved. Only if an entry was modified will the index be saved. To use `repair` you must enable `default.allowStoreUpdate`. It will fail if this property is not true.

`fail` will not change anything. It will fail during initialization if the index and folder do not match. If there is no index but one could be created it will be checked as if it was empty. If it fails it will not be created. When `fail` fails it will state all entries that it found to be in any state and all unowned files. It will list all broken, resolved and shared entries followed by unowned files. Misplaced, colliding and occupied entries can appear anywhere. They will be in the order of the rule description and unowned files will be listed by name. You do not need to enable `default.allowStoreUpdate` to use `fail`.

If there is no index and `default.allowStoreCreation` is false or the index is not a file directly within the folder it will fail before checking anything. The folder can be a link to another folder.
When a rule is saved it will write its violations to the file that its entry points to. Even if that is a symbolic link. The store will fail to save a rule and leave the index and folder in the state it was found. If the entry points to the index. This includes if it is a symbolic link or different spelling of the index file name. Points to a location that is not directly within the folder or. If the rule does not have an entry and its generated name points to something or is being used by another entry. If using `repair` and saving no violations for a known rule it will forget the rule. Its entry will be removed and its file as well. Unless another entry is sharing that file. In which case only the entry will be removed. Even if it points outside of the folder. If using `repair` and saving no violations for an unknown rule nothing will be saved. If it cannot delete the file it will fail to save and leave the entry. If there are violations the rule will be saved.

Multiple stores in the same process can initialize and save rules concurrently. It will always leave a index that can be read and a folder that contains the index and files from surviving entries. No store will check on a save that is currently happening.
