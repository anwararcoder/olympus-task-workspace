# Split posts and pages at page breaks

**Category**: Feature Request

Add support for splitting a post or page into several HTML pages at `PAGE_BREAK` markers. A marker is an HTML comment reading `PAGE_BREAK` in the compiled text, written `.. PAGE_BREAK` in reStructuredText and `<!-- PAGE_BREAK -->` in Markdown or HTML. It is matched like the teaser marker, regardless of case and surrounding spaces, and it may carry a label after a colon, as in `PAGE_BREAK: Getting started`. Text that only looks like a marker, such as a code sample, is not a break. Markers never appear in the output.

Each page holds the content between two breaks, in order, and a post without breaks still gets a single page. A break that would leave a page with nothing but whitespace is ignored, so a post with only one non-empty part is not split. When a break falls inside elements, such as a reStructuredText section, the page before ends them and the next page continues inside elements with the same tag and attributes except the `id`, which stays with the first part. A continued element that would hold nothing is left out, and an ordered list continued on the next page keeps counting from where it stopped.

The first page stays where the post is today. For a post without pretty URLs, page N goes next to it with `-N` added to the slug, as in `my-post-2.html`. For a post with pretty URLs, page N goes inside the post's folder at the path given by the new translatable `PAGE_BREAK_PRETTY_URL` setting. That setting is a list of path components using the `{number}` and `{index_file}` placeholders the way `INDEXES_PRETTY_PAGE_URL` does; it defaults to `["{number}", "{index_file}"]`, which gives `my-post/2/`. Whether a post has pretty URLs is decided per post, as it is today. When the new `PAGE_BREAK_SINGLE_PAGE` setting is true (it defaults to false), every split post also gets a single-page version holding its whole text, placed where a page numbered `all` would go: `my-post-all.html` or `my-post/all/`.

In every built-in theme, each page of a split post shows a navigation that links to each of its other pages. A page is named by the label of the last break before it, or by its number when that break has no label or the page is the first. The navigation also links to the previous and next page with `rel="prev"` and `rel="next"`, and to the single-page version when there is one; the single-page version links to every page. In the document head, the `prev` and `next` links walk the pages, so only the first page points back to the previous post and only the last page points on to the next post. The single-page version keeps the post's own head links. Pages after the first get ` (page N)` appended to their title, with "page N" in the page's language, such as `Mein Beitrag (Seite 2)` in German. Each page and the single-page version is its own canonical URL, and comments appear only on the last page and on the single-page version.

A link to an element of a split post by its `id` takes the reader to the page holding that element, wherever the link appears: in the post itself, in another post (including links made with the `doc` role or a `link://` magic link), on index pages and in feeds. On the single-page version, links to elements of its own post stay on that page. The `link://slug/...` and `link://filename/...` magic links accept a `page` argument, either a page number or `all`, and lead to the first page when the post has no such page. With teasers, the "Read more" link leads to the page holding the teaser marker; without them, index pages and feeds show the whole text.

Each translation is split by its own breaks. On page N, the links to other languages, both in the head and in the list of translations, point to that translation's page N, or to its first page when it has fewer pages. On the single-page version they point to the translation's single-page version when it has one, and to its first page otherwise. The sitemap lists every page and single-page version of the posts it lists, with alternate links following the same rule, and leaves out those of drafts, private posts and scheduled posts. When deploying leaves out a draft or scheduled post, it removes every page of that post. A page or single-page version whose output path is already generated for another post is reported the same way as two posts generating one file, and the build fails.

Pages and single-page versions are regular build targets, so `nikola check -f` reports no orphans after a build. A single build after editing a source brings everything up to date: the post's set of pages and their content, the language links on its translations' pages, and links to its elements from other posts.
