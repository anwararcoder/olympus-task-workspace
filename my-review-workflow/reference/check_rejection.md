# Problem Idea Rejection Reasons

This document lists common reasons why a **problem idea** may be rejected. It focuses on the core idea itself, not minor description issues or solution improvements.

---

## 1. Out of Repo Scope / Philosophy

- The problem proposes features outside the repository's intended scope.
- Examples:
  - Adding HTTP server to a CLI-only tool.
  - Adding configuration loader to a minimal argument parser.
  - Features that conflict with the library’s design philosophy (e.g., functional library receiving OOP changes).

---

## 2. Too Trivial / Simple

- Problems that require very minimal changes or one-liner solutions.
- Does not involve meaningful problem-solving or complexity.
- Examples:
  - Monkey-patching `window.alert`.
  - Simple date/time offset calculation when library already supports it.
  - Tiny modifications that do not challenge the developer.

---

## 3. Duplicate / Already Solved

- The functionality is already implemented in the repo.
- The new problem does not provide added value or learning opportunities.
- Examples:
  - Features already present in the codebase.
  - Minor wrappers around existing functionality.

---

## 4. Contradicts Library Design / Intentional Behavior

- The problem would violate the library's intended behavior or philosophy.
- Examples:
  - Trying to make union types behave differently from zod’s intended design.
  - Introducing type-unsafe paths in a type-safe library.
  - Modifying permissive behavior that is documented as intentional (e.g., Ramda’s path access rules).

---

## 5. Relies on Non-Fair or Artificial Data

- Problems that cannot be solved fairly without using provided solution data.
- Examples:
  - Including a fabricated JSON file required for solving.
  - Tests depending on hardcoded values or AI-generated content.

---

## 6. Invalid / Based on False Claims

- The problem proposes features that already exist.
- Claims in the problem are incorrect or not valid engineering gaps.
- Examples:
  - Wrapper for existing date parsing functions.
  - Feature that is already handled by the library (like timezone support).

---

## 7. Too Prescriptive / Over-Specified

- The problem dictates exact implementation details rather than observable behavior.
- Overly prescriptive problems reduce creativity and problem-solving.
- Examples:
  - Specifying exact placeholder syntax or error messages.
  - Forcing implementation of internal API patterns that are not necessary for observable outcome.

---

## 8. Implementation / Solution Out of Scope

- The required solution asks for rewriting or changing large parts of the repo.
- Examples:
  - Removing public API functions.
  - Massive framework changes for small utility features.
  - Introducing global state or large-scale structural changes.

---

## 9. AI-Generated / Not Original

- Problems suspected to be generated by AI without human verification may be rejected.
- Submissions must reflect original, thought-out problem ideas.
- Examples:
  - AI-generated tests and solutions.
  - Copying existing issues or PRs without adding real value.

---

## Notes

- Minor description issues, formatting, or focus on details **are not valid reasons for rejecting the problem idea**. These are considered feedback for improvement.
- Always ensure rejection focuses on the **core idea of the problem**.
