# Deterministic Duplicate Class Resolution

Add a `duplicate-class-strategy` option with the values `first`, `last`, and `error`; its default is `first`. Each registered context source is a distinct origin: two sources may share a human-readable name and are still separate origins. Any own decompilation source outranks every library. Within that highest-precedence tier, `first` and `last` use root registration order and child-context list order. `error` rejects candidates only when their exact classfile bytes differ; byte-identical candidates are allowed and use the first eligible origin. Repeated entries from one origin are not an inter-origin conflict. Reject an invalid option before processing and identify the accepted values.

A class family also has to stay on one origin. An exact binary-name duplicate among own sources activates origin coherence for its enclosing class family. Determine member families transitively from `InnerClasses` metadata and local or anonymous families from `EnclosingMethod` metadata; a literal `$` in a top-level binary name does not establish a family. When the family root is available, its selected origin anchors the family; otherwise the strategy-selected duplicate does. Load later members from that origin. If an encountered member is available only from another own origin, fail and identify the family root, member, anchored origin, and alternative origins. Metadata linkage alone does not combine origins: without an exact duplicate, load each class from its own source.

The same name selection applies to eager inputs and to eager or lazy libraries. Registering a source only records its candidates; nothing is resolved until a selection is requested, which is also when duplicate warnings and conflicts surface. A decompiler context caches the positive and negative lazy probes it makes along with the selections it resolves, and that state belongs to that context alone. Adding another context source invalidates the class and family decisions it affects, while `reloadContext()` discards prior duplicate-resolution and lazy-probe results before rebuilding them. Concurrent lookups or output processing must not change the winner.

The decision should be visible in the log and honest in the output. For differing candidates resolved by `first` or `last`, emit one warning per decision that identifies the binary name, strategy, selected origin, ignored origins in registration order, and metadata family root. An `error` conflict identifies every conflicting highest-tier origin. Return every selected own class once and emit it only through its selected origin's output sink. Losing duplicate entries are omitted, while nonduplicate classes and non-class resources remain with their original inputs.
