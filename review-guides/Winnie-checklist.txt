Repo & Docker environment
- Dockerfile builds cleanly from scratch
- Correct base image, correct WORKDIR, correct CMD
- Repo is permissively licensed and not stale
- Tests are deterministic across re-runs
- Tests run offline (no hidden network dependence)
- Framework discovery / runner config is sound

Problem description (the spec) quality
- Direct action opening, no motivation or external framing
- Outcome-based requirements, no implementation prescription
- Public API fully described (the solver never sees the tests)
- No leaked implementation details (algorithms, internal data structures)
- No non-ASCII, no --, plain natural punctuation
- Reads naturally, no AI slop, no redundancy, no headings

Test behavioral purity
- Tests assert observable behavior, not private internals
- No assertions on undeclared fields or internal state
- Content/format assertions removed when behavioral state is already covered (no double-pinning)
- Tests don't pin output format details such as error msg wording the spec never declared. Spec and tests shouldn't even pin output format details but should be behavioural so that output format is up to the solver, except for cases where the format itself is the requirement.

Test-to-spec alignment
- Every behavior the tests check is actually stated in the spec
- No implicit assumptions (empty input, error types, ordering) that the spec leaves silent
- Hidden output formatting (key order, casing, whitespace) is either declared or not required

Solution code quality
- No bugs in solution
- Solution is high quality code, follows good conventions or at least repo conventions
- Meaningful LOC meets the tier floor (real code, not comments/dead code/noise)
- Solution compiles and typechecks cleanly
- No unused imports
- No dead or unreachable code
- No model-reasoning comments (AI narrating its own steps)
- Comments/docstrings match repo convention
- API shape matches conventions of adjacent features in the repo
- solution.patch contains source files only, no test code or test-related code
- Patch hygiene: new files show --- /dev/null, applies cleanly, no full-staging corruption
- Consumer-surface completeness (e.g. new public API ships TypeScript declarations if the repo distributes them)

Test code quality
- No print/log/debug residue in tests
- No model-reasoning comments in test files
- Strict assertions: a wrong implementation cannot slip through (no loose >= 1 where exact count matters)
- Usage-style coverage: tests exercise every supported way to call the feature (sync/async, ESM/CJS, TS/JS, etc.)
- Mutation testing: deliberately wrong code must make a test fail
- Base/existing tests are never modified
- Test files named after the feature (no -new suffixes)
- No quest/platform names like "Olympus" or "Shipd" in test file names, functions, or constants
- test.patch contains test files + test.sh only
- No unused imports in tests

Behavioral correctness
- The reference solution actually implements the spec, not just passes the tests
- Adversarial testing against the spec finds no behavior the solution gets wrong
- No spec requirement left unimplemented

Fairness (from real solver runs)
- Failures classified as genuine difficulty vs unfair
- Ambiguity signal: 3+ agents failing the same way on something not derivable from the repo or spec = possibly unfair
- No environment/Docker/test.sh bug causing failures
- No test asserting behavior the spec contradicts or omits
- No output-format unfairness (right behavior, failed on undeclared format)
- Passing solutions inspected for gaming (hardcoded outputs, test-keyed special cases)
- Solver message depth meets the tier minimum
- Difficulty/pass-rate within tier bounds for the relevant family e.g Mars or Olympus

Philosophy & uniqueness
- Feature aligns with a genuine repo principle and is core, not niche
- No name, functional, or mechanism overlap with existing or accepted problems
- No overlap with open/closed PRs, issues, or Discussions
- No maintainer ruling against the API or design
- At today's HEAD, maintainers would still plausibly accept this feature
- Repo owns the majority of the feature's logic (not thin glue over a dependency)

catch-all
- Anything the focused checks missed
- Overall coherence between spec, tests, and solution
- Difficulty and substance befit the tier
